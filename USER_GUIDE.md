# PR Reviewer Service: Руководство по эксплуатации и интеграции

## 1. Введение

Данный документ описывает операционную семантику, доменные правила и ворклоу интеграции PR Reviewer Service. Руководство предназначено для системных архитекторов, DevOps-инженеров и технических лидов, ответственных за встраивание сервиса в существующие SDLC-процессы организации.

## 2. Доменная логика и правила автоматизации

Сервис реализует детерминированный конечный автомат и алгоритмы назначения для устранения ручного управления и обеспечения соответствия корпоративным политикам рецензирования кода.

### 2.1. Алгоритм назначения ревьюверов
При инициации нового запроса на ревью (`POST /api/v1/pull-requests`) система применяет следующую политику:
*   **Лимит емкости:** На один Pull Request назначается не более **двух (2)** ревьюверов.
*   **Исключение автора:** Инициатор (автор) PR строго исключается из пула потенциальных ревьюверов.
*   **Фильтрация по доступности:** В выборку попадают только инженеры с установленным флагом `isActive = true`. Персонал, находящийся вне зоны доступа (отпуск, больничный и т.д.), категорически игнорируется.
*   **Логика выбора:** Если количество доступных и активных членов команды превышает лимит, система алгоритмически определяет подмножество ревьюверов (текущая реализация ограничена рамками команды автора).

### 2.2. Неизменяемость состояний (Merge Lock)
Сущность `PullRequest` функционирует как строгий конечный автомат.
*   При переходе PR в состояние `MERGED` объект немедленно блокируется.
*   **Ограничение:** Система перманентно отклоняет любые последующие запросы на модификацию (переназначение ревьюверов, обновление метаданных) для закрытых сущностей.
*   **Цель:** Гарантия целостности истории ревью для целей комплаенса и аудита.

## 3. Интеграционный ворклоу

Для развертывания сервиса в новом организационном подразделении необходимо выполнить следующую последовательность API-операций.

### Этап 1: Организационное профилирование
Определение логической структуры инженерных групп.
*   **Действие:** Создание агрегата Team (Команда).
*   **Эндпоинт:** `POST /api/v1/teams`
*   **Требование:** Использование глобально уникального идентификатора команды.

### Этап 2: Управление идентичностью и жизненным циклом
Наполнение команд персоналом и управление их статусами доступности.
*   **Действие:** Регистрация пользователей (`Users`) и их ассоциация с командой.
*   **Эндпоинт:** `POST /api/v1/users` (или пакетная загрузка через профиль команды).
*   **Управление состоянием:** Флаг `isActive` должен синхронизироваться с актуальным статусом инженера. Рекомендуется автоматизация данной связи с HR-системами организации.

### Этап 3: Жизненный цикл ревью (CI/CD Интеграция)
Интеграция следующих эндпоинтов в вебхуки вашей VCS-платформы (напр., GitHub Actions, GitLab CI).
*   **Инициация:** Вызов `POST /api/v1/pull-requests` при создании PR в VCS. Ответ содержит массив `assigned_reviewers`.
*   **Обработка исключений (Переназначение):** Если назначенный ревьювер становится недоступен в процессе цикла, используйте специализированные эндпоинты для запроса ротации.
*   **Финализация:** При успешном слиянии (merge) в VCS необходимо инициировать обновление статуса в `MERGED` для фиксации аудиторского следа.

## 4. Операционный FAQ

**В: Как ведет себя система, если в команде автора нет других активных инженеров?**
*О: Система создаст сущность Pull Request, но вернет пустой массив ревьюверов. Слой интеграции должен корректно обрабатывать данный кейс, а администраторам необходимо либо добавить персонал, либо актуализировать флаги `isActive`.*

**В: Поддерживает ли система кросс-командное назначение ревьюверов?**
*О: В рамках текущих архитектурных ограничений выбор ревьюверов строго ограничен основной командой автора. Это минимизирует когнитивную нагрузку и гарантирует наличие доменного контекста у рецензентов.*
