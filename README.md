# PR Reviewer Service: Архитектурный манифест

## 1. Резюме (Executive Summary)

PR Reviewer Service представляет собой высокопроизводительное микросервисное приложение, предназначенное для автоматизации и обеспечения соблюдения политик код-ревью внутри инженерных команд. Система, спроектированная на принципах Чистой архитектуры (Clean Architecture), гарантирует детерминированное назначение ревьюверов, обеспечивает строгий аудит изменений и минимизирует операционные издержки менеджмента.

## 2. Архитектура системы

Сервис строго следует многослойному архитектурному паттерну для обеспечения разделения ответственности, тестируемости и долгосрочной поддерживаемости:

*   **Слой домена (Domain Layer):** Инкапсулирует ключевые бизнес-сущности (`User`, `Team`, `PullRequest`) и корпоративную логику. Слой полностью независим от внешних фреймворков и баз данных.
*   **Сервисный слой (Application Layer):** Оркестрирует доменные объекты для реализации бизнес-сценариев (алгоритмы назначения, переходы состояний).
*   **Слой инфраструктуры (Storage Layer):** Реализует интерфейсы персистентности с использованием PostgreSQL.
*   **Транспортный слой (Presentation Layer):** Предоставляет RESTful API для интеграции с CI/CD конвейерами и внешними VCS-платформами.

### 2.1. Системные требования
*   **Среда исполнения:** Go 1.25+
*   **СУБД:** PostgreSQL 16+ (рекомендуется дистрибутив Alpine для контейнеризированных сред)
*   **Контейнеризация:** Docker Engine & Docker Compose (v2+)
*   **Миграции:** Goose (интегрировано через Makefile)

## 3. Модель данных и оптимизация производительности

Реляционная схема нормализована и оптимизирована для высокой пропускной способности операций чтения, характерных для интеграций с CI/CD.

### Структура сущностей (ERD)
1.  `teams`: Корневой агрегат для организационных единиц.
2.  `users`: Инженерный персонал, ассоциированный с командами (связь N:1). Включает жизненный цикл через флаги (`is_active`).
3.  `pull_requests`: Конечный автомат запросов на ревью. Отслеживает переходы состояний (например, `OPEN` $\rightarrow$ `MERGED`).
4.  `pull_request_reviewers`: Таблица связей (N:M), сопоставляющая конкретных пользователей с PR в роли ревьюверов.

### Стратегия индексирования
Для обеспечения логарифмической $O(\log N)$ или близкой к константной сложности критических путей чтения применяются следующие B-Tree индексы:
*   `idx_users_by_team_id`: Оптимизирует получение состава команды. Критичен для алгоритма выбора ревьюверов.
*   `idx_pull_requests_by_author_id`: Ускоряет агрегатные запросы для пользовательских дашбордов.
*   `idx_pull_request_reviewers_by_reviewer_id`: Разрешает ограничение составного первичного ключа, обеспечивая высокоэффективный поиск ожидающих ревью для конкретного инженера.

## 4. Конфигурация окружения

Поведение системы управляется переменными окружения согласно методологии Twelve-Factor App. Конфигурация должна подключаться через файл `.env` или системы управления секретами (напр., HashiCorp Vault, Kubernetes Secrets).

```bash
# Инициализация базовой конфигурации
cp .env.example .env
```

**Обязательные переменные:**
*   `POSTGRES_URL`: Строка подключения к PostgreSQL.
    *Формат: `postgres://[user]:[password]@[host]:[port]/[db_name]?sslmode=[mode]`*
*   `SERVER_PORT`: Порт прослушивания HTTP (по умолчанию: `8080`).

## 5. Развертывание и эксплуатация

Сервис подготовлен для немедленного развертывания в контейнеризированных средах.

### 5.1. Контейнеризированный запуск (рекомендуется)
Инициализация полного стека через Docker Compose:

```bash
# Сборка и запуск в фоновом режиме
docker-compose up --build -d

# Проверка состояния контейнеров
docker-compose ps
```

### 5.2. Локальная разработка и отладка
Для запуска непосредственно в хост-системе используйте цели `Makefile`:

```bash
# 1. Запуск инфраструктурных зависимостей
docker-compose up -d postgres

# 2. Применение миграций
make migrate-up POSTGRES_URL="<connection_string>"

# 3. Компиляция и запуск
go run cmd/service/main.go
```

### 5.3. Контроль качества (QA)
CI-конвейер опирается на следующие инструменты верификации:
```bash
make lint    # Статический анализ кода (golangci-lint)
make test    # Выполнение unit/integration тестов с детектором гонок
make bench   # Запуск бенчмарков производительности слоя хранения
```
